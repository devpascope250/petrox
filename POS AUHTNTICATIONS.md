# Task: Implement Site Provisioning Keys and Mobile POS Device Authentication

## Objective

Implement a complete and production-ready POS/mobile-device provisioning system in the backend.

The system already has companies/sites/users and existing authentication. We need to introduce two new concepts:

1. `site_provisioning_keys` — temporary/one-time keys generated for provisioning a POS device to a specific site.
2. `site_devices` — registered POS/mobile devices that permanently belong to a specific site after successful provisioning.

**Important architectural requirement:**

> Everything related to POS/mobile-device provisioning, provisioning-key verification, device authentication, device registration, and device management APIs must live inside the backend's `mobile` module/folder.

Do not mix this logic into the existing employee/user authentication module unless an existing shared authentication utility is genuinely required.

Before modifying anything, inspect the existing backend architecture, Prisma schema, authentication system, authorization/permissions, module conventions, route/service/repository patterns, error handling, validation, and naming conventions. Follow the existing project's conventions instead of introducing a parallel architecture.

---

# 1. Database Models

Create the following tables/models.

## `site_provisioning_keys`

Purpose:

A provisioning key is generated by an authorized admin for a particular site. A POS enters the key once to become registered to that site.

Recommended fields:

```text
id
siteId
keyHash
expiresAt
usedAt
revokedAt
createdBy
createdAt
updatedAt
```

Requirements:

* `id` should follow the project's existing ID strategy.
* `siteId` must reference the existing site/company-site table.
* `keyHash` must contain a secure hash of the provisioning key.
* NEVER store the raw provisioning key in the database.
* `expiresAt` must be required.
* `usedAt` is nullable.
* `revokedAt` is nullable.
* `createdBy` should reference the admin/user who generated the key if the existing schema supports this relationship.
* Add appropriate indexes.
* Add indexes for `siteId`, `expiresAt`, and any lookup pattern required by the provisioning flow.
* Do not add unnecessary duplicated company information if the existing site relation already provides it.

A provisioning key is valid only when:

```text
key exists
AND key is not expired
AND key has not been used
AND key has not been revoked
AND the referenced site is active
```

After successful provisioning, the key must become unusable.

# 3. Device UUID

The POS will provide a device identifier/fingerprint during provisioning.

Example:

```json
{
  "activationKey": "QK-847291",
  "deviceUuid": "..."
}
```

The backend must treat the device UUID as a device identifier, NOT as a secret.

Do not assume that a hardware UUID alone provides authentication.

The permanent authentication credential must be separate from the device UUID.

Add an appropriate uniqueness constraint.

For example:

```text
unique(deviceUuid)
```

or, if the business rules require it:

```text
unique(siteId, deviceUuid)
```

Use the option that best matches the existing system and explain the choice in the implementation notes.

# 5. Admin: Generate Provisioning Key

Create an admin-protected endpoint for generating a provisioning key for a site.

Conceptually:

```http
POST /mobile/sites/:siteId/provisioning-keys
```

Request example:

```json
{
  "expiresInMinutes": 10
}
```

If the project's existing conventions use a different route structure, follow them.

The endpoint must:

1. Authenticate the admin.
2. Authorize that the admin can manage the requested site.
3. Verify that the site exists and is active.
4. Generate a cryptographically secure random provisioning key.
5. Hash the key before storing it.
6. Store the hash in `site_provisioning_keys`.
7. Set an expiration time.
8. Return the raw key ONCE in the API response.

Example response:

```json
{
  "key": "QK-847291",
  "expiresAt": "2026-10-05T09:40:00.000Z"
}
```

The raw key must NOT be stored.

The raw key must NOT appear in logs.

The raw key must NOT appear in database records.

# 6. Provision Device

Create the endpoint used by the POS to provision itself.

Conceptually:

```http
POST /mobile/provision
```

Request:

```json
{
  "provisioningKey": "QK-847291",
  "deviceUuid": "DEVICE-UUID",
  "deviceName": "POS 01"
}
```

The backend must:

1. Validate the request.
2. Hash/verify the supplied provisioning key.
3. Find the corresponding provisioning-key record.
4. Verify it is not expired.
5. Verify it has not already been used.
6. Verify it has not been revoked.
7. Verify the site exists.
8. Verify the site is active.
9. Verify the device UUID is acceptable.
10. Prevent duplicate device registration.
11. Create the `site_devices` record.
12. Mark the provisioning key as used.
13. Generate the permanent device authentication credential.
14. Return the device credentials and bootstrap information.

This entire operation must be **transactional**.

If device creation succeeds but key consumption fails, the entire operation must roll back.

Likewise, never allow two simultaneous requests using the same provisioning key to successfully provision two devices.

Handle race conditions appropriately using the database transaction/locking/unique constraints supported by the existing database.

# 8. Device Authentication

Implement a proper authentication mechanism for registered POS devices.

The important distinction is:

```text
Provisioning Key
    =
temporary onboarding credential

Device Credential
    =
permanent device authentication credential
```

After provisioning, the POS must no longer need the provisioning key.

Future requests should authenticate using the device's permanent credential.

The backend must be able to determine:

```text
deviceId
siteId
device status
```

from the authenticated device context.

For example:

```text
request
   ↓
device authentication
   ↓
deviceId
   ↓
siteId
```

Do not allow the POS to simply submit:

```json
{
  "siteId": "some-site"
}
```

and trust it.

The site identity must come from the authenticated device.

# 9. Site Isolation

This is extremely important.

A device registered to Site A must never be able to access Site B's data simply by changing a `siteId` parameter.

For every mobile/POS request requiring site-scoped data:

```text
authenticatedDevice.siteId
```

must be treated as the trusted site identity.

Example:

```text
Device:
  deviceId = POS-001
  siteId   = SITE-A
```

If the client sends:

```json
{
  "siteId": "SITE-B"
}
```

the backend must reject it or ignore the client-provided site ID according to the endpoint's design.

Never trust the client to determine the device's site.

# 15. Security Requirements

Implement all of the following:

### Provisioning keys

* cryptographically secure random generation
* short expiration
* one-time use
* hashed at rest
* never logged
* revocable
* transactional consumption
* race-condition safe

### Device authentication

* device credential must not be based solely on UUID
* secure token generation
* secure storage expectations documented for the Flutter POS
* revoked devices cannot authenticate
* expired/revoked credentials rejected
* no credentials returned from list endpoints

### Authorization

Every admin operation must verify authorization.

Every device operation must derive site identity from authenticated device context.
